1.  Descripción General
Esta evaluación corresponde a la Unidad 3 de la asignatura Programación Frontend. Continuarás con el mismo contexto de empresa o emprendimiento de las evaluaciones anteriores, pero ahora desarrollarás una intranet funcional usando React + TypeScript. La intranet debe permitir a usuarios internos gestionar información relacionada con el contexto de tu proyecto (agendamiento, inventario, control de pacientes, pedidos, etc.).
En esta primera entrega el sistema interactuará con localStorage para persistir datos. La migración a Firebase ocurrirá en la Evaluación Sumativa 4, que se evaluará sobre el mismo repositorio.

3.  Requisitos Técnicos de la Intranet
3.1  Repositorio GitHub (nuevo)
Para esta evaluación debes crear un repositorio nuevo en GitHub, independiente de los repositorios de las evaluaciones ES1 y ES2. El proyecto React debe vivir en este repositorio desde el primer commit.

✔	El repositorio debe ser público y contener únicamente el proyecto React/TypeScript de esta evaluación.
✔	El README.md debe documentar el contexto del proyecto, cómo ejecutarlo localmente (npm install, npm run dev) y una descripción de los módulos implementados.
✔	Los commits deben ser frecuentes, descriptivos y reflejar avance progresivo real. Cada commit debe representar un avance significativo e identificable (ej: "feat: implementar formulario de registro de paciente con validación", "feat: agregar listado de turnos con filtro por fecha").
✗	NO se acepta un único commit con todo el código terminado ni pocos commits con cambios masivos. Esto se considerará evidencia de desarrollo sin proceso y afectará directamente el criterio de commits.
✗	NO se acepta continuar sobre el repositorio de ES1 o ES2. El uso del repositorio antiguo será tratado como incumplimiento de instrucciones.

3.2  Autenticación y sesión de usuario
La intranet debe tener un sistema de login. Dado que en esta entrega aún no se usa Firebase Auth, el login simulado debe funcionar así:
- Credenciales válidas almacenadas como objetos en localStorage o como constante en el código.
- Al autenticarse, se guarda un objeto de sesión en localStorage con datos del usuario (nombre, rol u otro).
- Ese objeto de sesión debe compartirse en toda la aplicación mediante useContext (contexto de autenticación/usuario).
- Las rutas de la intranet deben estar protegidas: si no hay sesión activa, la app redirige automáticamente al login.
- Debe existir un botón de cierre de sesión que limpie el estado global y redirija al login.

3.3  Enrutamiento
La intranet debe contar con un sistema de rutas que permita navegar entre vistas sin recargar la página. Puedes usar React Router u otra solución, siempre que la justifiques y la domines. El docente puede pedirte que expliques el funcionamiento durante la demostración.
Al menos una ruta debe recibir un parámetro dinámico (ej: /paciente/:id, /producto/:id) que se lea con useParams para mostrar el detalle del registro seleccionado.

3.4  Módulos funcionales con CRUD en localStorage
La intranet debe contar con al menos dos módulos que permitan gestionar datos de forma completa. Cada módulo debe implementar:
- Formulario de registro: campos controlados con useState, validación de campos obligatorios y retroalimentación visual de errores.
- Listado dinámico: los registros se muestran con useEffect al montar el componente o al cambiar el estado. Debe existir al menos un filtro o búsqueda.
- Edición y eliminación: el usuario puede modificar un registro existente o eliminarlo, con confirmación visual.
- Persistencia: los datos se guardan y recuperan desde localStorage correctamente al recargar la app.

3.5  TypeScript
El proyecto debe estar desarrollado en TypeScript. Como mínimo:
- Todos los componentes deben tipear sus props mediante interfaces o types.
- Los objetos de datos (ej: Paciente, Producto, Turno) deben tener su interfaz o tipo definido.
- No se acepta el uso masivo de any como reemplazo del tipado real.
Los proyectos sin TypeScript serán evaluados con descuento en cada criterio donde TypeScript era aplicable.

3.6  Hooks requeridos
Hook	Uso mínimo esperado
useState	Control de campos de formulario, estados de carga, errores de validación y datos del listado.
useEffect	Carga inicial de datos desde localStorage al montar los componentes de listado; efectos dependientes de cambios de estado.
useContext	Acceso al contexto global de autenticación/usuario desde cualquier componente (nombre, rol, función de logout).
useParams	Lectura del parámetro dinámico de ruta para mostrar el detalle de un registro específico.

💡	Si implementas la funcionalidad requerida pero usas una alternativa al hook indicado (ej: prop drilling en lugar de useContext), el criterio correspondiente será evaluado con puntaje reducido o no logrado, según la justificación técnica.

4.  Demostración en Vivo (Ejecución Práctica)
El día de cierre de la evaluación cada estudiante clonará su repositorio en el equipo del docente y demostrará el funcionamiento en vivo. La demostración tiene un peso de 10 puntos sobre el total.

1	El docente solicitará navegar entre rutas, iniciar y cerrar sesión, crear registros, editarlos y eliminarlos.
2	Se realizarán preguntas técnicas: ¿Por qué usaste useContext aquí? ¿Cómo funcionan tus rutas protegidas? ¿Dónde defines la interfaz de este objeto? ¿Qué pasa si el array de dependencias de useEffect está vacío?
3	Se pueden pedir modificaciones en vivo: agregar un campo al formulario, cambiar la lógica del filtro, mostrar el nombre del usuario logueado en un componente diferente.
4	El docente revisará el historial de commits del repositorio para verificar el avance progresivo del desarrollo.

📋	Por cada pregunta que no puedas responder correctamente durante la demostración se descontarán 5 puntos de la nota final. Si el docente determina que no hay comprensión ni autoría del trabajo, la evaluación será calificada con nota mínima (1,0).
